# Airflow · Weather Dashboard

An Apache Airflow 3 project that fetches current weather + a 24-hour forecast
from [OpenWeather](https://openweathermap.org/api), stores per-city / per-run
snapshots on disk, and renders an interactive HTML dashboard with temperature
history and a forecast strip per city.

The project is structured around **multiple DAGs**: one single-city pipeline
plus a dynamic DAG factory that emits an independent pipeline per additional
city.

---

## Project Layout

```
airflow__orchestrate_weather_dashboard/
├── airflow/
│   └── dags/
│       ├── weather_pipeline_dag.py          # single-city DAG (CITY env)
│       └── weather_multi_city_dags.py       # dynamic factory: one DAG per city in CITIES
├── src/
│   ├── config.py                            # path helpers, env, slugging
│   ├── fetch_weather.py                     # OpenWeather /weather → raw JSON
│   ├── transform_weather.py                 # raw JSON → flat CSV row
│   ├── fetch_forecast.py                    # OpenWeather /forecast → raw JSON
│   ├── transform_forecast.py                # raw JSON → next-24h CSV
│   └── build_dashboard.py                   # renders per-city + index HTML
├── data/
│   ├── raw/<city>/weather_<ts>.json         # current-weather snapshots
│   ├── processed/<city>/weather_<ts>.csv    # flattened current weather
│   ├── forecast_raw/<city>/forecast_<ts>.json
│   └── forecast_processed/<city>/forecast_<ts>.csv
├── dashboard/
│   ├── index.html                           # multi-city overview (auto-refresh 60s)
│   └── <city>.html                          # per-city pages
├── .airflow/                                # AIRFLOW_HOME (cfg, db, logs)
├── .env                                     # API key + CITY/UNITS/CITIES
├── pyproject.toml                           # uv-managed dependencies
└── uv.lock
```

## Prerequisites

- **Python 3.14** (see `.python-version`)
- **[uv](https://docs.astral.sh/uv/)** for dependency / venv management
- An **OpenWeather API key** ([free tier](https://openweathermap.org/appid))

## Setup

```bash
# 1. Install dependencies into .venv
uv sync

# 2. Configure environment
cat > .env <<EOF
OPENWEATHER_API_KEY=your_api_key_here
CITY=Kathmandu
UNITS=metric
# Optional: comma-separated list of additional cities for the factory DAG.
# Defaults to "Pokhara,London,Tokyo". The factory skips whatever CITY is.
# CITIES=Pokhara,London,Tokyo,Sydney
EOF
```

## Running the Project (without Airflow)

Useful for quick smoke tests and for populating `dashboard/index.html` once.

```bash
# Run the full pipeline for a single city
PYTHONPATH=. uv run python -c "
from src.fetch_weather import fetch_weather_data
from src.transform_weather import transform_weather_data
from src.fetch_forecast import fetch_forecast_data
from src.transform_forecast import transform_forecast_data
from src.build_dashboard import build_dashboard, build_index_dashboard

city = 'Kathmandu'
transform_weather_data(city, fetch_weather_data(city))
transform_forecast_data(city, fetch_forecast_data(city))
build_dashboard(city)
build_index_dashboard()
"

# Open the result
xdg-open dashboard/index.html      # Linux / WSL
# open dashboard/index.html        # macOS
```

## Running with Airflow

Airflow is installed via `pyproject.toml`. The project uses a **local
`AIRFLOW_HOME`** at `./.airflow/` so nothing is written to your global
`~/airflow`.

### One-liner (dev only)

`airflow standalone` boots the api-server + scheduler + executor in a single
process and prints an auto-generated admin password to the console.

```bash
AIRFLOW_HOME="$PWD/.airflow" \
PYTHONPATH="$PWD" \
uv run airflow standalone
```

Open [http://localhost:8080](http://localhost:8080) and log in with the printed
credentials. The four DAGs appear automatically:

| DAG | Source | Description |
|---|---|---|
| `weather_dashboard_pipeline` | `weather_pipeline_dag.py` | Single city (`$CITY`, default Kathmandu) |
| `weather_pipeline_pokhara` | factory | Generated by `weather_multi_city_dags.py` |
| `weather_pipeline_london` | factory | Generated by `weather_multi_city_dags.py` |
| `weather_pipeline_tokyo` | factory | Generated by `weather_multi_city_dags.py` |

Unpause a DAG and trigger a run, or wait for the hourly schedule.

### Running components separately (closer to production)

```bash
# Terminal 1 — scheduler + DAG processor
AIRFLOW_HOME="$PWD/.airflow" PYTHONPATH="$PWD" uv run airflow scheduler

# Terminal 2 — API server / web UI
AIRFLOW_HOME="$PWD/.airflow" PYTHONPATH="$PWD" uv run airflow api-server
```

### Useful CLI commands

```bash
# List parsed DAGs
AIRFLOW_HOME="$PWD/.airflow" PYTHONPATH="$PWD" uv run airflow dags list

# Trigger a one-off run
AIRFLOW_HOME="$PWD/.airflow" PYTHONPATH="$PWD" \
  uv run airflow dags trigger weather_dashboard_pipeline

# Test a single task without writing to DB (great for debugging)
AIRFLOW_HOME="$PWD/.airflow" PYTHONPATH="$PWD" \
  uv run airflow tasks test weather_dashboard_pipeline fetch_weather_data 2026-05-12
```

> **Why `PYTHONPATH="$PWD"`?** The DAGs import from `src.*` (e.g.
> `from src.fetch_weather import fetch_weather_data`). Airflow needs the project
> root on `sys.path` so those imports resolve.

## Customizing Cities

The single-city DAG (`weather_dashboard_pipeline`) always runs for `$CITY`.
The factory DAG generates one independent DAG per name in `$CITIES`, **excluding
whatever `$CITY` is** so they don't race on shared output files.

```bash
# .env
CITY=Kathmandu
CITIES=Pokhara,London,Tokyo,Sydney,Bengaluru
```

After editing `.env`, the scheduler picks up new DAGs within a parse interval
(default ~30s). You can force a reparse with:

```bash
AIRFLOW_HOME="$PWD/.airflow" PYTHONPATH="$PWD" \
  uv run airflow dags reserialize
```

## Conventions / Practices

- **Per-city, per-run outputs.** Every fetch writes to
  `data/raw/<city>/weather_<UTC-timestamp>.json`. Transform reads the file path
  via XCom from the fetch task, so the raw/processed pair stays linked.
  Nothing is overwritten; history accumulates for the trend chart.
- **City as a parameter, not a global.** `src/` functions all take `city` as
  a kwarg; there is no module-level `CITY` constant. This is what lets the
  factory generate N independent DAGs from the same code.
- **XCom for run-scoped values, env for config.** API key, default city, and
  the city list come from `.env`. The raw-file path generated by a fetch task
  is passed to its transform via XCom (`{{ ti.xcom_pull(task_ids='...') }}`).
- **Airflow 3 imports.** `PythonOperator` is imported from
  `airflow.providers.standard.operators.python`, not the deprecated
  `airflow.operators.python`.
- **Timezone-aware UTC.** `datetime.now(timezone.utc)` everywhere
  (`datetime.utcnow()` is deprecated in Python 3.12+).
- **Local AIRFLOW_HOME.** `.airflow/` is gitignored; `airflow.cfg` points
  `dags_folder` at `airflow/dags/` so there's no copy-deploy step.
- **Idempotent DAGs.** `catchup=False`, hourly schedule, `retries=3` with a
  2-minute backoff. Re-running a task simply overwrites that timestamp's file.

## Known Limitations

- All four hourly DAGs run `build_index_dashboard` at the end, so they race on
  `dashboard/index.html` when they fire on the same hour boundary. The page is
  consistent (last writer wins; they read the same data), but the proper fix
  is a separate Asset-triggered dashboard DAG — planned next.
- The history chart needs accumulated hourly runs to look like a trend; the
  first few hours after enabling a city show only one or two points.
- OpenWeather free tier: 60 calls/min, 1 000 000 calls/month. The current
  setup uses 2 calls per city per hour (weather + forecast), well under the
  cap.
